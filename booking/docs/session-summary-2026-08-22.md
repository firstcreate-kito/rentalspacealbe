## 2. 決定事項

### 基盤・設計
- リポジトリは `booking/` 配下のモノレポ
- Workers制約対応：パスワードは Web Crypto PBKDF2／トランザクションは `db.batch()`／時刻はドメイン純関数へ注入／定期処理は Cron Triggers
- 料金計算は**純関数化**し、キャンペーン×割引手段を**2軸モデル**で厳密化（テーブル駆動テストで固める）
- ダブルブッキング防止＝**条件付きINSERT（原子的排他）**

### メール／プライバシー
- メール配信＝**SendGrid（事業者名：Twilio Inc.）**。到達率のためドメイン認証(DKIM/SPF)・DMARC・専用サブドメイン・バウンス自動抑制
- プライバシーポリシー委託先：Cloudflare / SendGrid(Twilio) / Google / LINEヤフー / Stripe（海外は「外国にある第三者提供」欄に記載）

### 決済
- **Stripe 一本**（PayPal 不採用）
- 初期の決済手段＝**カード／Stripe銀行振込／コンビニ払い（Stripe系のみ）**
- **自社口座への振込（請求書払い）は初期スコープ外**（概念・スキーマは保持し運用後に対応）

### 変更・キャンセル・返金（承認ゲート方式）
- **全ての変更・キャンセルは管理者承認で確定**。セルフ即時操作は**なし**
- **会員ランクは概念・スキーマのみ保持し当面は無効化**（基準・特典は運用後に策定）
- 返金・追加課金の**計算と実行はシステム（Stripe API）、引き金は管理者承認**（管理者はStripe画面を触らない）
- **返金・追加課金の両方**が承認ゲート対象（追加課金でも変更リクエストが飛ぶ）
- **承認画面で管理者が金額を上書き調整できるのを標準**（理由メモ必須・監査証跡）。不承認→手動Stripeは最終手段
- **返金経路は支払方法依存**：カード＝自動返金／Stripe銀行振込・コンビニ＝**顧客に口座を伺い銀行振込返金**
- 値上がり差額のカード自動課金で本人認証が必要な場合＝**メール認証リンクのフォールバック**
- **申請時は枠を保持、承認時に解放**
- **申請受付期限＝利用日当日まで**
- **キャンセル料は既存の策定済みポリシーを適用**（実値は未提供）

### 非同期入金・書類
- コンビニ・Stripe銀行振込は**入金通知（Webhook）で確定**。`held` で枠確保・期限切れ失効
- 振込／払込の**案内は画面表示だけにせず、メール＋マイページ再表示で必ず届ける**（金額・期限・予約番号を明記）
- **請求書は確定時に自動発行・顧客メール送付**／初期は**領収書もすべて自動発行**

### UI
- マイページの「予約変更リクエスト」モーダル内に、**キャンセルポリシー／変更ポリシーをアコーディオン表示**（画面遷移なし・モーダル重ねなし）。**プロトタイプ実装済み**（`booking/web/change-request-modal.html`）

## 3. 未確定事項（要確認）
- **料金**：2軸モデルの最終確認、最低時間割れの単価、ポイント付与基準、消費税の内訳
- **マスタ実データ**：各スペースの営業時間・課金方式・時間帯区分・平日/土日祝単価、GCalカレンダーID、祝日データ取得元。※LPは「日額・ダイナミックプライシング」だが本システムは「時間帯別固定単価＋即時予約」で**事業モデルが異なる**点の合意
- **キャンセル料率の実値**（例：◯日前まで無料／◯日前◯％／当日◯％）
- SendGrid：直契約か代理店（構造計画研究所）経由か、送信サブドメイン名、DMARC運用
- コンビニ・Stripe銀行振込の**領収書自動発行**の承認（推奨：自動）
- 返金期限（約180日）超過時に銀行振込へ切替する運用の承認
- 管理者承認をメールリンクでも行うか（暫定：管理画面ボタン中心）
- ポリシー本文の格納先（単一管理）
- ブラックリスト拒否文言／書類公開URLの有効範囲／Bookly移行マッピング
